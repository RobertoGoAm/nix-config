* Merge requests reviewed inside Herdr

Every Herdr space on a GitLab or GitHub repository gets an MRs tab beside its Notes,
Kanban and Backlog: the repository's open merge requests on the left, and the
one picked on the right as a diff to read and comment on with nvim's keys.
It is for going from one merge request to the next without leaving Herdr,
and for seeing them change while the tab stays open. tuicr stays for the
phone, whose Herdr app shows terminals only: =t= on a merge request opens it
there in a new tab.

The list puts the merge requests waiting for my review first, then mine,
then everyone else's, each with its pipeline, its approvals, how many of its
threads are still open, its size and when it last moved. It is fetched every
two minutes, whether the window is in front or not, and at once when the
window comes back after half a minute away. The merge request on the right is
read again when the list says it moved on: a push, an approval, a pipeline
that finished; the cursor stays on its line, and nothing reloads while a
comment is being written.

A request that comes in, or that starts asking for my review, is announced
once with a Herdr notification, which shows the tab when clicked, and carries
a dot in the list until it is opened. A tab's first list only learns what is
there. The requests panel leaves those announcements to the tab for a
repository that has one, and opens a request clicked there in the tab rather
than in a tuicr tab of its own; =t= finds the request's tuicr tab before
opening another.

The diff is every file in one list, each line's threads under it and my
drafts under those, and at the end the threads that sit on no line: the
merge request's conversation, and threads whose line a later push took
away. Where I was in each merge request is kept per space, so coming back to
one puts the cursor on the same line; it is saved every few seconds as the
cursor moves.

Long lines wrap, at a space where one is near, onto rows of their own marked
=↪= and without numbers, each still the line it belongs to, so a comment there
lands on it. =w= lets them run on instead, and =<= and =>= move the code
sideways then; the choice is kept. The diff moves sideways by keys rather
than by a scroller, as the list of rows takes the trackpad's sideways
scrolling for itself.

=m= marks a file read, as GitHub's "Viewed" does: it folds down to its
header and the cursor goes on to the next unread file, the header counts
them (=3/16 read=), and the mark is saved at once, with the place. The mark
holds a digest of the file's diff, so a push that changes the file brings it
back unread, and one that leaves it alone keeps it folded. =m= on a folded
file unfolds it.

My comments are GitLab draft notes, as in GitLab's own review: nobody sees
them until =S=, pressed twice, publishes them all at once. A draft shows in
the diff where it will land, and =D= on it drops it.

| Keys        | What they do                                                  |
|-------------+---------------------------------------------------------------|
| =n= =e=     | down and up: a line in the diff, a merge request in the list  |
| =h= =i=     | to the list and back to the diff (=i= or =enter= opens one)   |
| =ctrl-d/u=  | half a page                                                   |
| =gg= =G=    | top and bottom                                                |
| =]f= =[f=   | next and previous file                                        |
| =]c= =[c=   | next and previous change                                      |
| =]t= =[t=   | next and previous thread or draft                             |
| =m=         | mark the file read, folding it away, or unfold it again       |
| =w=         | wrap long lines, or let them run on                          |
| =<= =>=     | move run-on lines sideways                                    |
| =tab=       | next merge request (=shift-tab= the previous one)             |
| =v=         | select lines, for a comment on all of them                    |
| =c=         | comment on the line, or on the selection                      |
| =C=         | general comment, on the merge request rather than a line      |
| =r=         | reply to the thread under the cursor                          |
| =x=         | resolve the thread, or reopen it                              |
| =D=         | drop the draft under the cursor                               |
| =a=         | approve, or take my approval back                             |
| =S=         | publish every draft (asks for a second =S=)                   |
| =y=         | copy =path:line=, for a Claude session                        |
| =o=         | open the merge request in the browser                         |
| =t=         | open it in tuicr                                              |
| =R=         | fetch everything again now                                    |

=h n e i= move, as in nvim here (=hnei, as in nvim= in =herdr.org=). In the
comment box =⌘↵= saves the draft and =esc= gives up on it.

An agent's merge request comes here rather than to tuicr: the review hook in
=tuicr.org= labels the agent's terminal with it, and this space's tab selects
it the next time it is drawn, without being shown; the agent's PR pill and
=Cmd+Shift+R= show the tab on it. The agent reads the drafts back with
=mr-review show=, and leaves publishing them to me.

=requests= opens the tab with the others, for every space whose folder has an
=origin=, on GitLab or GitHub. A space on another machine is reviewed through
the checkout at the same path on this computer, found from its terminals'
folder; without one it gets no tab. A tab closed stays closed for that space, and the
new-space dialog has it as a fourth companion to tick.

** The forge side

The tab asks =mr-review= (=mr-review.sh=) for everything and gets one JSON
answer per call, so the mod holds no GitLab knowledge and the helper can be
tried from a terminal: =mr-review list .= in a checkout. =glab= does the
talking, with the host and project of the folder's =origin=:

- =list= is one GraphQL query for every open merge request with its
  reviewers, approvals, pipeline, thread counts and diff size, where the REST
  list would need a request per merge request for half of those.
- =show= makes its five requests (the merge request, its diffs, discussions,
  drafts and approvals) at once and waits for the slowest.
- =comment=, =reply=, =undraft=, =resolve=, =approve=, =unapprove= and
  =submit= each make one change.

A comment on several lines carries GitLab's =line_range=, whose ends are
named by line codes: the SHA-1 of the file's path and the old and new line
counters at that line, both of them even on a line only one side has. The
mod keeps those counters on every row it draws for that.

=show= also colours the code. Each file's old side (its context and removed
lines) and new side (context and added lines) go through =bat= as two files
of their own, hunks run together, with bat's =ansi= theme: the sixteen
terminal colours, which the tab paints in Herdr's theme, so the diff takes
the same colours as the terminals beside it. PHP is named outright, as a
hunk rarely has the =<?php= bat would switch PHP on from. A file too large
or generated, or one bat fails on, is drawn plain.

A repository on GitHub goes to =mr-review-github= (=mr-review-github.sh=),
which answers the same calls in the same shapes, so the tab knows one helper.
GitLab's draft notes are GitHub's pending review there: one per pull request
and person, seen only by them until it is submitted. A comment on lines is a
thread of that review, a reply a pending reply in a thread, and a comment on
the whole pull request goes into the review's own body. =S= submits it as a
comment; =a= submits it as an approval, drafts and all, since GitHub keeps one
review in the making. Pull requests a GitHub App opens in a repository of mine
(an agent's) count as waiting for my review. The colouring both use is
=mr-review-highlight.sh=, put before each script.

Errexit stays off: =show='s requests run in the background and each records
its own exit code, which errexit would end before it was written.

#+begin_src nix
{ pkgs, ... }:
let
  highlight = builtins.readFile ./mr-review-highlight.sh;
  tools = [
    pkgs.bat
    pkgs.coreutils
    pkgs.gawk
    pkgs.git
    pkgs.gnused
    pkgs.jq
  ];
  options = [
    "nounset"
    "pipefail"
  ];
  mrReviewGithub = pkgs.writeShellApplication {
    name = "mr-review-github";
    runtimeInputs = tools ++ [ pkgs.gh ];
    bashOptions = options;
    text = highlight + builtins.readFile ./mr-review-github.sh;
  };
  mrReview = pkgs.writeShellApplication {
    name = "mr-review";
    runtimeInputs = tools ++ [
      pkgs.glab
      mrReviewGithub
    ];
    bashOptions = options;
    text = highlight + builtins.readFile ./mr-review.sh;
  };
in
{
  home.packages = [ mrReview ];

  home.file.".config/herdr-app/mods/mrs" = {
    source = ./herdr-app/mrs;
    recursive = true;
  };
}
#+end_src
