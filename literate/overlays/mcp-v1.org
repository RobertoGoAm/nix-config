#+TITLE: overlays mcp-v1

#+PROPERTY: header-args:nix :tangle (my/lit-target) :comments org :mkdirp yes

* Two packages still write mcp 1.x against an mcp 2.x in the set

nixpkgs moved =mcp= from 1.x to 2.2.0, and 2.x renames the thing both of these
reach for:

  ModuleNotFoundError: No module named 'mcp.server.fastmcp'. This is mcp 2.x,
  where FastMCP was renamed to MCPServer

=semgrep= is not a test failure dressed up as one. =semgrep/cli.py= imports
=semgrep.commands.mcp=, which imports =FastMCP= at module scope, so the import
fails before any command runs -- the build happens to notice it in conftest,
and a shipped =semgrep= would be a binary that cannot start.

=mcp-proxy= says so in its metadata rather than in a traceback: it declares
=mcp<2,>=1.27.1=, and =pythonRuntimeDepsCheckHook= compares that against the
2.2.0 in the closure and stops. It is what =serena-shared= in
=features/cli/claude.nix= runs as its stdio bridge, so it takes Serena with it.

nixpkgs kept =mcp_1= -- 1.29.0 -- in the python set for exactly this, so
neither package needs patching. They need the argument they were written for.

** Scoped to the two of them, not to the set

Replacing =mcp= across =pythonPackagesExtensions= would hand 1.29.0 to
everything, including whatever has already been ported to 2.x. So =semgrep=
takes =mcp_1= through its own =override=, and =mcp-proxy= -- which asks for
=python3Packages= whole rather than for =mcp= -- gets a package set with that
one attribute swapped.

Both entries stop mattering the day their upstreams port, and the cost of
leaving one behind is an override that resolves to the same thing twice.

#+begin_src nix
final: prev: {
  pythonPackagesExtensions = prev.pythonPackagesExtensions ++ [
    (pyFinal: pyPrev: {
      semgrep = pyPrev.semgrep.override { mcp = pyFinal.mcp_1; };
    })
  ];

  mcp-proxy = prev.mcp-proxy.override {
    python3Packages = prev.python3Packages.overrideScope (
      _pyFinal: pyPrev: {
        mcp = pyPrev.mcp_1;
      }
    );
  };
}
#+end_src
